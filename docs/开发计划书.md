## 0. 需求确认（我对项目的理解，请核对）

**一句话**：你是亚马逊运营，要做一个**自用**的"商品图 → AI 规划 → 批量出图"工作台，把平时靠人工问 AI 的 A+ 图 / 主图 / 视频流程**固化成可复用的软件**，对标"AI 详情图"类产品，但**用你自己的 API 网关，且提示词 / 模型 / 流程全部可配置**。

我理解的核心链路：

```
上传商品参考图(多角度, 首张为主参考) + 可选卖点 brief
  → [规划 Job] 多模态 LLM 按规划提示词输出结构化 Plan(JSON: product/design_spec/modules[])
  → 用户在页面上编辑方案 → 确认
  → 对每个 module：编译出图提示词(模板+变量) → [出图 Job] 图像编辑模型(带参考图) 生成
  → fit 裁剪缩放到画布(默认 1464×600, 保留 _raw)
  → [质检 Job] 确定性检查 + VLM 商品一致性 + VLM 文字校验
  → 通过入库 / 不通过自动重试(≤N, issues 追加进 AVOID) / 仍失败标红人工放行
```

**价值排序**（做取舍时依此判断）：① 出图模型能力（多参考图图像编辑，保证商品一致）→ ② 提示词体系（分层、可编辑、版本化）→ ③ 规划/质检用 VLM（稳定出 JSON 即可）→ ④ 质检与局部重生成（决定可用率）。

**已定决策**（不再讨论）：
- 所有模型调用**只走 OpenAI 兼容接口**（你已有网关和 Key），不写厂商原生适配器
- 部署 **Docker 单镜像 + 数据卷**，优先跑 NAS；不做 Windows exe
- 自用单用户，仅可选访问密码；后端 FastAPI / SQLite；前端 **Vue 3 + Vite + Element Plus，纯 JS**（用户确认：去掉 TypeScript 与 Pinia，状态用 Vue 自带 reactive/composables 实现，降低工程复杂度）——对 PLAN_v2 §0 技术栈的已确认修订
- **不引入 Celery / Redis / PostgreSQL**；进程内 worker + 任务表，进度用 **SSE**
- 首个预设 `aplus_banner`（1464×600）；主图预设第二、视频第三
- 文字模式可切换：`model`（模型直出短标题）| `blank_then_overlay`（留白后贴字，小字一律走此模式）
- 一切可复现：每个 asset 存编译后提示词、模型、参数、参考图哈希、预设版本；重出=新 asset 不覆盖

**如上理解有偏差，请指出；无偏差则按此执行。**

## 3. 执行计划（里程碑与任务拆解）

> M0 由你执行；M1 不写死任何模型名，等 M0 结论填充 §5 开放项。

**M0（你执行）**：在网关上跑 `poc/poc.py`，对比 2–3 个出图模型（`.env.example` 格式），观察：商品一致性、文字错误率（标题 vs 小字）、对宽横幅的裁切表现、速度与单价。产出结论写入 §5。

**M1 骨架与链路（后端可独立先行）**
1. 脚手架：`app/backend`（FastAPI + SQLite + 迁移）与 `app/frontend`（Vite + Vue 3 + Element Plus，纯 JS，无 TS/Pinia）
2. `setting` 表 + 加密存储（`APP_SECRET` 主密钥）+ 设置页（连接、角色→模型映射、并发、单价）+ "测试连接"（对每角色发最小请求）
3. `providers/openai_compat.py`（按 §2 映射重构，含单测）
4. 项目创建：multipart 多图上传（排序、首张主参考）+ brief + 预设选择
5. `services/planner.py` + 规划 Job + Plan 页面只读展示（编辑放 M3）
6. 内置预设导入：`planner.system.md` / `image.template.md` 内容写入 `preset_version` v1
- **验收**：上传一款商品得到与 poc 同结构的 Plan；各角色"测试连接"通过

**M2 出图与画廊**
1. `services/compiler.py` + 提示词预览接口
2. 出图 Job + 并发上限（每角色默认 2）+ 启动时 `running→queued` 恢复
3. `services/imaging.py` fit + `_raw`
4. SSE `/api/projects/{id}/events`；画廊按模块分组；单张下载；`export.zip`
- **验收**：5 模块出图成功；重启容器任务可续；每张 asset 元数据完整（prompt/model/mode/params/ref_hashes/preset_version/plan_revision）

**M3 可调化**
1. Plan 编辑（字段级，保存为新 revision, `source=user_edit`）
2. 单图"改提示词重出 / 换模型重出"（新 asset，`parent_asset_id` 链接，前端版本并排对比）
3. 预设管理：编辑器（分栏）、版本历史、回滚、"用样例商品试跑一张"
4. 品牌档案 CRUD + 编译时注入
- **验收**：改任一提示词重出产生新版本可对比；回滚预设后结果可复现

**M4 质检与运营**
1. `services/qa.py` 三段：确定性（尺寸/格式；主图白底、占比、最小边长——阈值在预设配置）→ VLM 一致性（`score/color_ok/shape_ok/logo_ok/details_ok/issues`，阈值默认 4）→ VLM 文字校验（与 headline/subline 比对，`blank_then_overlay` 时要求无文字）
2. 自动重试（issues → AVOID，≤`max_auto_retries`）→ `needs_review` 标红 → 人工放行（记录覆盖结果）
3. 成本统计（`/api/stats/cost`，单价在角色映射中配置）
- **验收**：构造商品变色坏样例能判不通过并自动重试；成本页与记录一致

**M5 主图预设**：确定性模式（rembg 抠图→白底画布→校验，`WITH_REMBG=1` 构建参数）+ 副图复用引擎；主图平台规则做成预设阈值。
**M6 视频预设**：`video` 角色、镜头脚本规划、已确认图作首帧、图生视频长任务（提交→轮询→入库）。

**测试要求**（贯穿）：`compile_prompt`、`extract_image`（多响应形态样例）、`fit`、JSON 解析容错、任务恢复、质检解析必须有单测；外部模型调用用录制的假响应。

## 4. 从对标产品样例（参考_详情页规划方案预览.txt）看到的差距

该 txt 是对标产品对同一款 UNBEGUN 内胆包的真实方案输出。对比 PoC 的 Plan schema，它**多出的字段**值得在 M3 做预设版本 v2 时吸收（通过预设可配置，不改死代码）：

- **商品身份类**：母视角策略（单实例、单请求 1 张、禁止多视角合体）、外观身份锚点（logo 位置/拉链细节逐项列出）、保真执行模式（"商品层保护合成/像素冻结"这类强约束语句）
- **版式类**：产品占比 / 文案占比的百分比、文案区域精确描述、安全边距 6%
- **设计系统类**：主色/辅助色/点缀色十六进制值、字体名与字重、字号层级、图标风格、跨图一致性锚点、摄影统一基准（色温/布光）

这些与 PLAN_v2 "扩展为整体设计规范＋逐模块方案"的方向一致，建议作为 `aplus_banner` 预设 v2 的 schema 增强项；PoC schema（`planner.system.md`）仍作为 v1 基线先跑通。

## 5. 开放项（等 M0 结果或你确认）

1. 出图主力/备选模型及各自 `mode/size`（edits 还是 chat；原生尺寸能否接近 1464×600）
2. 文字模式默认值（取决于 M0 观察到的标题/小字错误率）
3. 质检 VLM 用哪个模型 + 一致性阈值
4. 视频模型及网关接口形态（异步提交+轮询 or 同步）
5. 品牌档案固定字段（M3 前你补充）
6. 网关 `BASE_URL` 是否就绪、是否所有角色共用一个 Key
